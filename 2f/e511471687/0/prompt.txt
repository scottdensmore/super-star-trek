**Should-fix 1 — "real terminal, unusable TERM" is the same bug, and the fix is three lines.** `/home/scottdensmore/Developer/scottdensmore/super-star-trek/tui.c`, `tui_init()`. Two reachable cases survive:

- Real pty + `TERM=nosuchterm` (or `TERM` unset under `env -i`, a serial console, a typo'd export): `initscr()` calls `exit()` from inside the library. The player asked to play Star Trek and got `ncurses: cannot initialize terminal type` and exit 1 — no banner, no game, no hint that dropping `-t` would work.
- Real pty + `TERM=dumb`: `isatty` is true so curses starts, but `dumb` has no `cup` capability, so only `+- Quadrant ----+- Status ---+` ever reaches the screen. The message window never appears, typed input produces nothing, and the game looks hung. This is Emacs `M-x shell`, which is a mainstream way for a developer to run a CLI game.

Both are closable with the same non-fatal probe. I verified the API behaves as needed:

```
TERM=xterm      setupterm rc=0  cup=present
TERM=dumb       setupterm rc=0  cup=ABSENT
TERM=nosuchterm setupterm rc=-1        (returns ERR, does NOT exit)
TERM unset      setupterm rc=-1        (returns ERR, does NOT exit)
```

So in `tui_init()`, before `initscr()`: `int err; if (setupterm(NULL, STDOUT_FILENO, &amp;err) == ERR) return FALSE;` and reject when `tigetstr("cup")` is `NULL` or `(char *)-1` (needs `&lt;term.h&gt;`). Both fall into the existing fallback with a suitable message. I'd argue this belongs in *this* branch — it is the same one-sentence bug ("`-t` must never leave the player without a game"), and leaving it out means issue #5 gets closed while the more embarrassing variant (a hard crash on a real terminal) stays open.

### Builds and linking (the point you flagged)

Both trees configure and build clean: **Debug 0 warnings, Release 17** — the unchanged pre-existing `-Wunused-result` set, nothing new from `tui.c` or `osx.c`.

`setupterm`/`tigetstr` do link, but I want to be precise about *why*, because your instinct was right that this is fragile:

- On this box (and on the `ubuntu-latest` runners, same Debian packaging) `setupterm`, `tigetstr` and even `cbreak` live in **libtinfo.so.6, not libncurses.so.6**. The link only succeeds because `/usr/lib/x86_64-linux-gnu/libncurses.so` is a **linker script** containing `INPUT(libncurses.so.6 -ltinfo)`, so `-lncurses` transitively drags in `-ltinfo`. The built binary's `DT_NEEDED` confirms both.
- I proved the dependency is real by linking the same objects against `-l:libncurses.so.6` (bypassing the script): **`undefined reference to symbol 'cbreak@@NCURSES6_TINFO_5.0.19991023'`**.
- **macOS: no risk.** Apple's ncurses is not split — `libncurses.dylib` carries the terminfo entry points, and `term.h` ships in the SDK. `find_package(Curses)` there resolves everything in one library.
- **Residual risk: a distro that splits tinfo without providing the linker script** would fail to link with the current `target_link_libraries(sst PRIVATE ${CURSES_LIBRARIES} m)`. That is a build break, as you say, not a test failure. Neither CI platform is affected, so I am not calling it a blocker — but the one-line hardening is cheap if you want it, and CMake has already computed the answer during configure (`NCURSES_LDFLAGS:INTERNAL=-lncurses;-ltinfo` sits in the cache from pkg-config):

  ```cmake
  find_library(TINFO_LIBRARY tinfo)
  if(TINFO_LIBRARY)
    target_link_libraries(sst PRIVATE ${TINFO_LIBRARY})
  endif()
  ```
