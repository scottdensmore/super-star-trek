### 2. `pgrep -P` + `kill -STOP`/`-CONT` — sound, with one blind spot

Probed rather than reasoned (script kept at `/tmp/.../scratchpad/probe.sh`):

- **Target.** `#{pane_pid}` is the pane's shell on the script's private per-PID socket. `pgrep -P` restricts to its direct children; measured, there is exactly one — the `sst` process (`env` execs into it, so no intermediate). It cannot reach a process the suite did not start. The only theoretical escape is PID reuse between the `display-message` and the `kill`, which needs the pane shell to die and its PID to be recycled inside a few milliseconds; the value is read live from the server immediately before use, so there is no stale-PID window of the kind that would matter.
- **Bad input is guarded.** `pgrep -P ""` and `pgrep -P notanumber` both exit 2 with empty stdout (procps-ng 4.0.4), so `gpid` is empty and the `[ -z "$gpid" ]` branch fails the arm rather than signalling anything. (Cosmetic: pgrep's usage text then lands on the test's stderr, i.e. inside the ctest failure dump.)
- **No stopped process can be left behind.** Measured: game STOPped, then `tmux kill-server` (what `cleanup()` does, and what every trap routes to) — the pane shell dies, the process group is orphaned with a stopped member, the kernel delivers SIGHUP+SIGCONT per POSIX, and the game exits. Probe printed `OK: stopped game reaped when the pane shell died`. There is no `set -e` and no `exit` between STOP and CONT, so only a signal can cut in, and INT/TERM/HUP/PIPE/EXIT all reach that cleanup. The one uncovered case is SIGKILL of the script itself (ctest timeout escalation), which already leaks the private tmux server for any failure in this file; the stopped game dies with the server whenever it is killed. Not a new class of leak.
- **The blind spot, and it points at a false pass rather than a safety problem.** Neither arm asserts that the process it stopped is the game. If some platform's pane shell had another child listed first, `head -1` would stop that, the game would stay awake, the SIGWINCH coalescing the arm depends on would not happen, and `want_quadtitle` would pass — the arm testing nothing and saying so nowhere. A one-line guard (`ps -o comm= -p "$gpid"` is `sst`, or the state reaches `T`) would close it. On this machine the child *is* `sst` and the arms do fail on a mutant, so they have teeth here; this is about the day they are run somewhere else. Reporting, not fixing.
- Incidentally, the arms add a dependency on `pgrep` and job-control signals to a script whose header documents only its fractional-`sleep` requirement. Both CI platforms have `pgrep`; if it were missing the arms would *fail*, not skip.

## Findings

### 1. `game_pid()`'s `ps -o comm=` check is Linux-specific and will probably fail the macOS CI leg

`/home/scottdensmore/Developer/scottdensmore/super-star-trek/tests/tui.sh:147`

```sh
[ "$(ps -o comm= -p "$gpid" 2&gt;/dev/null)" = "sst" ] || return 1
```

POSIX defines the `comm` keyword as *"the name of the command being executed (argv[0] value) as a string"*. Linux `procps` deviates: it takes `comm` from `/proc/pid/stat`, i.e. the executable's basename. BSD/macOS `ps` follows the POSIX wording and prints argv[0] — which here is the absolute path. My probe on this machine shows exactly that argv[0]:

```
gpid=2033768  ps -o comm= =&gt; [sst]  ps -o args= =&gt; [/home/.../build/ci-debug/sst -t tournament 7 short novice pw]
```

On macOS the comparison would therefore be `/Users/runner/.../sst` = `sst` → false → `game_pid()` returns 1 → both new arms fail with *"pin slept drag: could not find the game process to stop"* and *"pin slept pause: ..."*. `.github/workflows/ci.yml` runs `macos-latest` for both presets, installs tmux, and `CI` is set, so `tests/tui.sh` runs there for real rather than skipping.

Loud, not silent — so it is a CI failure, not a false pass. I could not verify it on macOS from here; treat the confidence as high-but-unmeasured. The shape that works on both is matching the basename (`${c##*/}`, a `case` glob, or `-o ucomm=`).

Related nit, same helper: `pgrep -P "$shpid" | head -1` takes the lowest-pid child, where the file's own pre-existing `sigwinch_caught()` (`tests/tui.sh:3570`) loops over *all* children precisely because the first one need not be the game. The `comm` check makes a wrong pick fail loudly rather than quietly, so this is robustness only.

### 2. `slept_drag()` still does not assert that the drag happened

`/home/scottdensmore/Developer/scottdensmore/super-star-trek/tests/tui.sh:164-177`

The two guards you added close the "was the game really stopped" hole. The other precondition is unguarded: the two `tm resize-window` calls are fire-and-forget, and nothing checks that the pane ever reached 24 rows or came back to 40. ### The `clearok` question — my judgment: **keep the call**

I reproduced your proof independently. Copy of the working tree outside the repo, `sync_size()`'s `clearok(curscr, TRUE)` alone removed (the other two are indented deeper, so the substitution provably hit only line 1241), fresh `ci-debug` configure and build inside the copy, then `tests/tui.sh build/ci-debug/sst Debug` from inside the copy: **`tui OK`, exit 0**. Your claim is accurate.

I then went after the path itself rather than the test. `sync_size()` has exactly one caller, `tui_refresh_panels()`, and that has exactly six call sites — all in `/home/scottdensmore/Developer/scottdensmore/super-star-trek/tui.c`:

| site | context | already repainted? |
|---|---|---|
| 1746 | `tui_init()` | startup; no drag can precede it |
| 1756 | `tui_gameover()` | **no reader — this is the call's sole ground** |
| 1897 | `tui_readline()` pre-`wgetch` | healed one `wgetch` later by `KEY_RESIZE` |
| 1938 | `tui_readline()` `KEY_RESIZE` | own `clearok` immediately before |
| 2010 | `tui_getch()` pre-`wgetch` | healed one `wgetch` later |
| 2035 | `tui_getch()` `KEY_RESIZE` | own `clearok` immediately before |

So the path is real and narrower than the comment implies: `finish()` at `/home/scottdensmore/Developer/scottdensmore/super-star-trek/finish.c:72` calls `tui_gameover()` and *then* prints the entire epilogue and score before any read. Keep it, for three reasons:

1. **It is the sole repair at `tui_gameover()`**, and that repaint is followed by the longest unread output stretch in the game.
2. **Cost is nil.** `sync_size()` returns early unless the layout or terminal actually moved, so the `clearok` runs only on a genuine drag.
3. **Removing it puts the pinned-drag repair entirely on ncurses delivering `KEY_RESIZE` for a resize that does not change the size ncurses computes** — an undocumented implementation detail, and precisely the mechanism this whole change exists to work around. Belt-and-braces at zero measurable cost is the right trade here.

**But the stated reason it cannot be tested is wrong, and it matters.** Three places say the obstacle is the countdown's duration — `tui.c` beside the call ("that countdown runs in under a second end to end here, ... too short to drag a window across from a script"), the `pin drag` arm in `tests/tui.sh`, and #184's "Why it is hard to test".

I landed a resize inside the countdown on the first try, using the SIGSTOP trick `slept_drag()` already uses. Duration is not the obstacle. The obstacle is that `sync_size()` **is never called during the countdown at all** — `tui_puts_slow()` calls `wrefresh(wmsg)`, not `tui_refresh_panels()` — so both builds are displaced throughout it, and the real and mutated builds diverge only in the interval between `tui_gameover()`'s repaint and the first `wgetch`. I measured that interval by polling `capture-pane` as fast as it goes (≈5 ms/poll), three runs each:

```
REAL   run1: healed after 1.0086s     MUTATED run1: healed after 1.0091s
REAL   run2: healed after 1.0085s     MUTATED run2: healed after 1.0085s
REAL   run3: healed after 1.0057s     MUTATED run3: healed after 1.0050s
```

Indistinguishable. Your conclusion is right; the reason under it is not.

This changes #184's fix options. "Slow the countdown under a test-only hook" and "find another output-without-read stretch long enough to drag across" would both **not work** — lengthening output *before* `tui_gameover()` does not widen the window that has to be sampled. What would work is lengthening the unread output *after* it, and at `LINES=30` the epilogue hits the pager pause, which is a reader that heals the mutated build. That is the sentence worth putting in #184.

This is the class AGENTS.md step 4 singles out: the sentence that says *why*, which a reviewer cannot dispute without redoing the work. I redid it.
