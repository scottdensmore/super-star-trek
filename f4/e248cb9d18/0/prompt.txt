The cause: `sst.doc` has CRLF line endings (`file` reports "ASCII text, with CRLF line terminators"), and `helpme()` strips only the `\n`, leaving a trailing `\r` on every line. In plain mode the terminal prints the text, then CR, then LF — fine. In ncurses, `waddstr` writes the text, the `\r` returns the cursor to column 0, and then `skip(1)`'s `\n` **clears the line from the cursor to end** before wrapping. I confirmed the mechanism with a minimal curses probe:

```c
waddstr(w, "LINE-A plain");    waddstr(w, "\n");
waddstr(w, "LINE-B with CR\r"); waddstr(w, "\n");
waddstr(w, "LINE-C plain");    waddstr(w, "\n");
```
renders as `LINE-A plain`, a blank line, `LINE-C plain`.

Worth its own issue. The fix is one line in `helpme()` (strip a trailing `\r` as well as `\n`), or more defensively in `tui_puts()`. It also means any future output line ending in `\r` will silently vanish in TUI mode, which is worth a note in AGENTS.md alongside the existing "all output through `prout`" rule.

## The byte-identity question

You're right to ship it. Three arguments, in the order I find them persuasive:

**1. The rule cannot mean what a literal reading says, and the project has already established that.** AGENTS.md's byte-identity clause sits in the `sst -t` section, immediately after "raw `printf`/`putchar`/`fgets` silently bypasses the full-screen mode." Its subject is *the TUI must not leak into plain mode*. Read literally as "plain-mode bytes are frozen", it would have forbidden PR #19, which changed plain mode far more materially than this does — the game now prints `[Transmission ends.]` and exits where it previously looped for ever. That was unambiguously correct. So the operative question isn't "did bytes change" but "did anything a plain-mode player relies on change", and here nothing did.

**2. The removed bytes were never intentional output.** They aren't the game's text; they're an artifact of `sst.doc`'s line endings leaking through a `strlen(buf)-1` that assumed LF. Deleting them makes plain mode print what the author of `sst.doc` wrote, which is a stricter reading of fidelity than preserving them.

**3. It is not actually invisible in plain mode — it's an improvement there too.** `text\r\n` is a no-op on a raw terminal, but `sst | less` on `main` shows `^M` at the end of every help line (`less` only suppresses CR with `-r`/`-R`), as does any editor opening a captured transcript. So the branch improves the plain-mode experience for anyone paging or logging the manual. That's the argument I'd put in the commit body, because it converts "harmless change" into "fix".

I also agree with rejecting the `tui_active`-conditional variant, and I'd reject it more strongly than you did: it would mean the two modes render the manual from *different string data*, which is precisely the divergence the AGENTS.md rule exists to prevent. Conditioning on the display mode to preserve a byte-identity rule whose purpose is to prevent display-mode-conditional behaviour would be self-defeating.

**Should-fix — record the exception instead of leaving it implicit.** This is the one place I'd push back on process rather than substance. The value of a byte-identity rule is that it's mechanical; the moment "this diff is fine because it's invisible" becomes a judgement call made in a PR description, the rule stops being enforceable by anyone who wasn't in the conversation. Two cheap things close it: (a) restate the AGENTS.md clause as what it means — no *unintended* plain-mode change, with intended ones called out in the commit — and (b) pin the new state in `tests/journey.sh`, which already asserts no ESC bytes.
